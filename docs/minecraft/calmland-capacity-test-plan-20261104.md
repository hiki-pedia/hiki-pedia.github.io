2026-11-04~05 측정. **첫 공개 정원은 10명 이하를 권한다.** 5·10·15명은 연결 유지·같은 지역 이동·분산 이동의 기본 수치 기준을 통과했다. 10명은 추가 30분 분산 이동도 통과했다. 20명은 분산 배치 예열의 30초 평균 TPS가 15 아래로 내려가 중단했다.

| 판단 | 확인한 근거 |
|---|---|
| 공개 정원 후보 10명 | 30분 전원 접속·이동 유지, TPS 20.00, p95 41.28ms·p99 49.57ms·최대 85.58ms |
| 15명은 여유 감소 | 분산 이동 p95 45.40ms·p99 67.04ms. 기본 기준 통과지만 공개 정원으로 채택하기 전 추가 경계 반복 필요 |

| 원본 복구 | 마지막 시험 종료 후 원본 파일 543개 불변, 운영 healthy·재시작 정책 복구, 프록시 상태 응답 확인 |

측정 종료 시 운영 정원은 2명이었으며, **2026-11-05 후속 사용자 지시로 10명을 적용했다.** 설정 파일을 백업한 뒤 정상 종료·수정·재기동했고, healthy와 프록시 상태 응답 `max=10`을 확인했다. 이전 설정 백업은 서버2 `/data/nostos/backups/manual-capacity-10-20261105-093757/`에 보관했다. 이 결과는 체력 고정 더미의 통제된 오버월드 걷기 조건이다. 실제 플레이어의 고속 비행·대형 농장·레드스톤·네더 신규 생성·외부 회선 성능을 보장하지 않는다.

이 성능 측정은 CalmlandMap **1.12.0** 고정 조건이다. 이후 2026-11-05의 1.13.0 목줄 동행 확장은 별도 기능 검사 9개, 1.14.0 신규 랜덤 스폰·지급 대기 확장은 11개 검사로 검증했으며 전체 부하 시험을 새 버전으로 반복한 것은 아니다. 측정 자동화의 플러그인 해시와 복원 백업도 당시 조건으로 고정돼 있으므로 새 버전 재측정 시 기준을 명시적으로 갱신해야 한다.

실행 도구와 현재 범위는 측정 도구 안내 (`README.md`)에 정리했다. 서버1의 별도 평지 fixture에서 26.3/프로토콜777 로그인, 5분 연결 유지, 서버 좌표 표본 61개·서로 다른 위치 7개, 계측 유실 0, 재접속과 명령 전송을 확인했다. **평지·Peaceful 호환성 검증이며 운영 수용량 결과가 아니다.** 본 시험 복원본은 운영 Easy·AI를 유지한다.

첫 준비 시 자동 재시작 정책을 끄지 않아 운영 서버가 백업 중 재기동했다. tar 검증 실패로 부하 시험에 진입하지 않고 운영 healthy를 확인했다. 해당 백업은 사용하지 않는다. 자동화를 수정해 종료 전 `restart=no`를 확인하고, 정지 유지 검증 및 종료 경로의 기존 정책 복원을 추가했다. 실패 기록도 실행 증거에 보존한다.

### 예비 측정과 방법 보완

| 단계 | 관측 | 판정 |
|---|---|---|
| 서버2 0명, 예열 5분·측정 5분 | 약 20TPS, p95 0.17ms, 메모리 raw peak 986MiB, 유실·OOM 0 | 유휴 기준선 확보 |
| 초기 5봇 연결 유지, 측정 5분 | 약 20TPS, p95 12.27ms·p99 22.53ms·최대 129.28ms, raw peak 1009MiB | **무효:** 봇 1명 익사로 유효 인원 4~5명. 5인 통과 근거로 쓰지 않음 |

초기 시험은 운영 SSD(`/dev/sda2`)와 다른 HDD(`/dev/sdb1`)에서 실행된 점도 확인했다. 위 값들은 수집기·봇 검증 기록으로만 보존하고 최종 성능 비교에 합치지 않는다. 최종 시험 월드는 운영과 같은 SSD의 `/home/dnhs02/nostos-runtime/capacity-tests/` 아래에 두고, 실행 전 `st_dev` 일치를 강제한다. 백업·결과만 `/data`에 저장한다.

초기 경로는 목적지만 육지인지 확인해, 클라이언트가 중간 물가에서 파쿠르에 실패했다. 운영 원본 파일 535개 해시가 유지됐고, 종료 후 healthy·기존 재시작 정책·정원 2명을 확인했다.

재시험에서는 **폭 3칸의 평평한 육지가 이어지는 경로**를 서버에서 탐색하고 한 칸 간격으로 안내한다. 지형을 새로 만들거나 운영 월드를 바꾸지 않는다. 봇의 제작 기능 부족을 보완하기 위해 시험 복사본의 봇에만 철 방어구·핫바 스테이크 64개를 동일하게 준비하고, MCC auto-eat 2.0.2로 정상 식사하게 한다. 난이도·몹 AI·반려동물 지급은 유지한다. 사망 이벤트와 최신 유효 인원 감소를 감지하면 즉시 중단한다.

**사용자 요청으로 최종 시험 프로필(v3)은 체력 고정으로 변경했다.** 시험 봇과 해당 반려동물의 피해 이벤트만 취소해 최대 체력을 유지한다. Creative·관전·invulnerable 플래그를 쓰지 않아 몹이 계속 공격 대상으로 삼는다. 경로 이탈을 줄이기 위해 시험 봇의 넉백 저항을 1로 두고, 근처 폭발의 지형 파괴도 막는다. 일반 몹은 정상적으로 피해를 받으며, 운영 설정은 바꾸지 않는다. 1000 피해를 주는 실제 Paper 검사에서 플레이어 체력 20·길들인 늑대 40 유지, 몹 AI·공격 대상 유지, 일반 몹 사망을 확인했다. 피해 방지·폭발 방지 횟수는 구간별로 기록한다. 이 프로필은 **접속·통제된 이동·청크·AI 부하**를 위한 것이며 실제 생존 전투나 고속 탐험을 보장하지 않는다.

SSD에서 일반 체력으로 실행한 5명 A·B는 각각 p95 13.06ms·15.41ms로 통과했다. C는 좀비에게 봇이 사망해 무효 처리했고 원본을 복구했다. 일반 체력 시도와 v3 결과를 합쳐 집계하지 않는다.

이후 B는 같은 지역의 통제된 경로 이동, C는 분산 지역의 통제된 경로 이동으로 측정한다. C는 분산 청크·AI·메모리 비용을 관찰하며, 장거리 연속 탐험·고속 비행의 수용량을 대신하지 않는다. 초기 무효 시도와 보완 후 결과를 합쳐 통계를 내지 않는다.

## 1. 판단할 질문

1. 현재 자원 한도에서 5·10·15·20개 정상 접속을 유지할 수 있는가?
2. 같은 장소 생활보다 분산 이동에서 청크·메모리·틱 부하가 얼마나 증가하는가?
3. 최초 지급 반려동물, 비행·귀환 등 현재 기능을 사용했을 때 달라지는가?
4. 접속 실패가 게임 서버 자원, 설정 제한, 부하 발생기 중 어느 쪽에서 발생했는가?

로그인만 보내거나 서버 목록 핑만 보내는 프로그램을 플레이어 부하로 세지 않는다. NPC 엔티티를 20개 생성한 결과도 실제 클라이언트 접속 20개와 구분한다.

## 2. 실행 배치와 원본 보호

- 시험 대상은 **서버2의 별도 컨테이너**다. 같은 CPU·디스크·DB 동시 실행 조건을 사용한다.
- 유지보수 시간에 운영 게임을 정상 종료하고 검증한 콜드 백업을 확보한다. 부하 시험과 운영 게임을 동시에 실행하지 않는다. 운영 원본 디렉터리는 시험 컨테이너에 마운트하지 않는다.
- 시험 경로에 백업을 복원한다. 서버1 백업 사본의 파일 검증·독립 기동까지 기록하면 복원 훈련의 일부 근거로도 남길 수 있다. 봇 시험의 오프라인 UUID는 실제 온라인 UUID와 다르므로 플레이어 데이터 복원 검증 전체를 대체하지 않는다.
- 시험 서버는 서버2 루프백의 별도 포트(후보 25579)에만 바인딩한다. 서버1 부하 발생기는 SSH 터널로 이 비공개 포트에 연결한다. 터널은 시험용이며 운영 공유기·DDNS·포트포워딩은 바꾸지 않는다.
- 운영 Nginx를 경유하지 않는 1차 시험이므로 결과는 **게임 백엔드 수용량**이다. SSH 암호화·터널 처리량의 비용도 기록한다. 공개 회선·프록시·정품 인증의 종합 접속 성능과 혼동하지 않는다.
- 서버1에서 봇을 실행하고 서버2에서 게임을 실행해 발생기와 시험 대상을 나눈다. 서버1의 기존 웹·Airflow·Prometheus와 경쟁하는 정도도 측정한다. 서버1이 병목이면 봇을 맥 등 별도 장비로 옮긴 뒤 재시험한다.
- 시험 후 시험 서버를 정상 종료하고 봇·터널을 종료한다. 운영 서버를 원래 경로·이미지·설정으로 시작해 healthy·상태 응답·정원·원본 해시를 대조한다. 시험 데이터는 원본에 병합하지 않는다.

시험 중에도 DB·WireGuard·모니터링은 유지한다. 정기 05:00 백업과 겹치지 않는 점검 창을 선택하고, 공용 백업 잠금과 운영 복구 담당 프로세스를 확인해 자동 작업과 충돌하지 않도록 한다. 다른 서비스 중지·호스트 cache drop·강제 GC를 시험 준비 절차에 넣지 않는다. 장시간 유지보수가 어렵다면 시험을 단계별 날짜로 나눠 매번 운영 복구를 확인한다.

## 3. 고정할 설정

| 항목 | 시험 기준 |

시험 시작 전 실제 설정·원본/시험 마운트·프로세스·포트와 해시를 출력해 대조한다. 버전 변경, 메모리 증설, 최적화 플러그인 추가를 같은 실험에 섞지 않는다.

## 4. 봇 도구 적합성부터 검증

현재 도구는 **Minecraft Console Client 2.0 Early Access 13**이다. Linux x64 배포 SHA-256을 확인하고, 평지 접속 시험과 실제 지형 복사본의 식사·5분 이동 시험을 통과했다. 실제 지형 좌표 표본에서 약 298블록 이동·최저 체력 20·음식 소비를 확인했다. 도구 배포·계측·자동화 해시는 실행별로 보존한다. 아래 항목은 후속 시험에서도 계속 확인한다.

- 닉네임이 고정된 봇의 로그인·월드 입장, 청크 수신·처리, keepalive 응답.
- 서버가 인정하는 좌표 변화·이동, 장애물 대응 또는 검증한 경로 추종.
- 아이템 사용·명령 전송·로그아웃·재접속 자동화.
- 일정 시간(최소 5분) 생존 및 연결 유지, 예외·프로토콜 파싱 오류 없음.
- 수신 청크·바이트·접속/입장 시각·연결 종료 이유 기록 가능 여부.

단순 접속만 가능하면 그 결과는 연결 유지 시험에만 사용한다. 이동을 콘솔 텔레포트로 대신하면 실제 걷기/비행과 다른 부하이므로 별도 시험으로 표시한다. 봇이 청크를 소비하지 않아 정상 플레이보다 가벼워지거나 패킷 해석 실패로 무거워지는 경우는 본 시험에 쓰지 않는다.

현재 Mineflayer 안내는 26.3 정식 지원 미완료다. 이름이 유명하다는 이유로 바로 채택하지 않는다. 봇 도구를 맞추려고 운영 Paper를 내리거나 운영에 프로토콜 변환 플러그인을 추가하지 않는다. 도구 검증이 실패하면 이 단계에서 계획을 조정한다.

공식 근거:
- [MCC 릴리스](https://github.com/MCCTeam/Minecraft-Console-Client/releases): Early Access Build 9에 26.3 지원 명시. 후속 빌드의 호환·스크립트 동작은 직접 확인 필요.
- [Mineflayer 26.3 지원 논의](https://github.com/PrismarineJS/mineflayer/discussions/4190).

## 5. 본 시험 순서

먼저 0명 기준선을 5분 예열·5분 측정한다. 이후 N=5→10→15→20 순으로 진행한다. N명 모두 정상 입장한 시각을 기록하고, N명 도달 실패는 불완전한 표본으로 따로 기록한다.

각 N에서 아래 세 시나리오를 별도 복원본으로 실행한다. 정상 입장은 기본 5초 간격으로 한다. 같은 출발지 IP에 대한 운영의 접속 제한이 있으므로 이를 시험 복사본에서 확인하고, 제한으로 발생한 거절을 CPU 수용량 부족으로 분류하지 않는다. 본 측정 전에 자동 지급 반려동물을 수령하도록 움직이고 실제 생성 수를 기록한다(N명당 최대 3N마리).

| 시나리오 | 예열 / 본 측정 | 행동과 확인 목적 |
|---|---|---|
| A. 연결 유지 | 2분 / 5분 | 전원 입장·청크 처리 후 같은 구역에서 대기. 연결·플레이어·반려동물의 기본 비용 |
| B. 같은 지역 이동 | 3분 / 8분 | 약 128×128블록의 준비한 경로를 일정 속도로 순환. 청크 공유 시의 이동·AI·전송 비용 |
| C. 분산 탐험 | 3분 / 10분 | 보더 안의 서로 다른 구역으로 분산해 걷기. 경로 좌표·속도·실제 로딩 청크·중복률을 기록. 청크 로딩 증가 측정 |

테스트용 초기 배치는 운영 원본을 바꾸지 않고 복사본에서만 한다. 배치와 순간이동 부하를 예열/별도 구간으로 남기고 본 걷기 창과 섞지 않는다. 경로는 고정하고 이동 성공률·위치 표본으로 실제 행동을 검증한다. 20명이 모두 다른 청크 영역을 유지할 수 있다고 가정하지 않고 관측한 공유 정도를 보고한다.

연결 유지 합격만으로 N명 운영 가능이라 판단하지 않는다. A~C를 모두 통과한 범위를 본다.

### 기본 시험 후 집중 시험

| 시험 | 방법 | 결과 구분 |
|---|---|---|
| 기능 혼합 | 합격 후보 N에서 10분. 일부 봇은 3분 비행, 일부는 실제 침대 리스폰 설정 후 동물과 귀환. 귀환은 5분 쿨타임 준수. 블록 설치·파괴·상자 접근은 봇 지원 확인 후 포함 | 기능별 명령 성공·실패·시간과 CoreProtect 기록량 |
| 재접속 집중 | 운영과 같은 접속 제한을 유지한 복사본에서 N개 접속 요청을 짧은 간격으로 시도 후 정상 간격과 비교 | 설정 제한·인증 제외·자원 부족을 나눠 보고 |
| 네더 신규 생성 | 오버월드 합격 후보 N에서 신규 생성 구간을 5~10분 이동 | 사전 생성 오버월드와 별도 정원/주의사항 판단 |
| 지속 부하 | 최종 후보 N에서 30~60분 혼합 행동 | 힙·청크·엔티티 증가·Full GC·연결 안정성 확인 |
| 저장 영향 | 시험 복사본에서 save-all flush, 종료·재기동을 별도 창으로 측정 | 정상 플레이·저장·콜드 백업 중단을 구분 |

처음부터 모든 N에 모든 시나리오를 3회 반복하지 않는다. 탐색 1회 후 경계 정원과 그 아래 정원을 같은 조건으로 2~3회 재시험한다. 높은 단계가 실패하면 그 이상의 강제 부하를 계속하지 않는다. OS 디스크 캐시는 강제로 비우지 않고 이전 실행의 warm-cache 영향을 한계로 기록한다.

## 6. 무엇을 어떻게 수집할 것인가

| 대상 | 수집 주기·방법 | 보고할 값 |
|---|---|---|
| 전체 틱 처리 시간 | 시험 전용 Paper 계측, 각 tick의 처리 ms와 monotonic 시각을 버퍼에 모아 비동기 일괄 기록 | 틱 수, 평균·중앙·p95·p99·최대 MSPT, 50/100/500ms 초과 비율 |
| TPS | 원시 틱 수/구간 실제 경과 시간, spark 상태는 교차 확인 | 안정 구간 처리율·저하 지속 시간 |
| CPU·한도 | 1초 cgroup cpu.stat 차분, 호스트 CPU | 평균·최대·throttled periods/시간 증가 |
| 컨테이너 RAM | 1초 memory.current·memory.stat·memory.events | raw 메모리와 working set 구분, peak·OOM 이벤트 |
| JVM | 기존 jvm-perf-sample.py 계열 hsperfdata 1초, 가능하면 GC 로그 | heap 추세·GC 횟수/누적 시간, 로그가 있을 때 실제 pause 분포 |
| 청크·엔티티·플레이어 | 5초 시험 계측, 봇 좌표 표본 | 차원별 로딩/틱 청크·엔티티·실제 접속 수 |
| 디스크·네트워크 | 1초 호스트·컨테이너 counters, Prometheus 15초는 개요용 | I/O·대기·전송량·포화 구간 |
| 봇·발생기 | 봇별 로그와 서버1 자원 1초 | 요청→로그인/입장 완료, 끊김 이유, 수신 청크·바이트, 스크립트 지연 |
| 상관관계 | 단계 시작/종료/예열/배치/명령 타임라인 | 지연이 어느 활동과 겹쳤는지 |

기존 observe-player-session·jvm-perf-sample·요약 도구의 안전한 부분을 재사용하되, 기존 수집기는 운영/유휴 전제가 있으므로 시험 컨테이너·프로필을 인자로 받도록 먼저 분리한다. 무심코 기존 기본 컨테이너에 실행하지 않는다.

30초마다 받은 spark의 최근10초 p95들을 평균내어 전체 p95라고 부르지 않는다. 전체 MSPT 분위수는 각 단계의 원시 tick 표본으로 계산한다. 원시 tick 계측은 시험 전용 CapacityProbe로 구현했다. API의 tick duration과 monotonic 시각을 기록하고, 유실 수 및 enqueue 처리 비용을 함께 남긴다. 0명/1봇 예비 시험에서 동작을 확인했으며, 계측이 완전히 없는 실행과 동일하다고 가정하지 않는다. 수집 유실과 통계 제외 구간을 보고한다. Prometheus 그래프만으로 시험의 최악 지연을 계산하지 않는다.

JFR heap inspection과 강제 GC는 기본 시험에서 사용하지 않는다. GC counter의 누적 시간과 한 번의 최장 정지는 다른 값이다.

## 7. 판정과 중단 기준

아래 수치는 이 프로젝트에서 시험 전에 고정할 운영 목표이며 게임 전체의 공식 보장치가 아니다.

**정원 후보 통과:** 예열을 뺀 A~C 본 측정에서 실제 N명 유지, 평균 tick 처리율 19.5TPS 이상, p95 MSPT 50ms 미만, 비정상 연결 종료·서버 재시작·OOM 없음. p99/최대 및 청크 공급 지연이 크면 평균이 통과해도 보류한다. 메모리는 증가 추세가 수렴하고 자연 GC 후에도 여유가 남아야 한다.

**즉시 중단 또는 단계 실패:**
- TPS 15 미만이 30초 이상 지속하거나 수 초 단위 멈춤이 반복됨.
- OOM·프로세스 종료·watchdog 중단·지속적인 명령 불응답.
- 호스트 가용 RAM 1GiB 미만 또는 컨테이너 한도 95% 이상이 30초 지속.
- 지속적인 swap-out/I/O 대기와 틱 저하가 동반되거나 기존 DB 등 다른 서비스에 이상이 나타남.

**시험 무효·재설계:**
- 목표 N명에 못 미친 상태로 측정하거나, 봇이 이동·청크 처리를 하지 못함.
- 봇 발생기가 CPU·RAM·SSH 처리량 때문에 요청을 제대로 만들지 못함.
- 원시 지표 누락으로 통계 신뢰성이 깨짐, 백업·DB 배치 작업 등 다른 부하가 겹쳐 조건이 달라짐.

5분 이동평균 CPU가 낮다는 이유로 합격하지 않는다. 메인 스레드 병목·GC·청크 공급 지연을 함께 판단한다.

## 8. 정원 결정·산출물·예상 시간

예를 들어 10까지 안정적이고 15에서 반복 실패하면 최초 공개 정원은 5~10에서 선택한다. 20까지 통과해도 20을 실제 유저 보장치로 쓰지 않고 10~15로 시작해 운영 여유를 두는 판단이 가능하다. 정원 증가는 시험 결과와 실제 사용자 피드백을 함께 보고 결정한다.

표현은 **“현재 설정에서 더미 N개, 특정 행동·기간의 시험을 통과했다”**로 한정한다. 실제 유저 N명의 대형 농장·레드스톤·모든 행동을 보장하지 않는다. 내부망·오프라인 인증 시험으로 WAN 업로드·인터넷 지연·계정 인증 서비스의 수용량을 주장하지 않는다.

### 남은 검증

기본 정원 탐색과 10명 30분 분산 지속 시험은 완료했다. 기능 혼합(3분 비행·동물 동행 귀환·블록 작업), 네더 신규 생성, 저장 영향, 15명 경계의 동일 조건 반복, 실제 계정·외부 회선 검증은 이번 결과에 포함하지 않았다. 권장 정원을 넘기거나 다른 플레이 조건을 보장하려면 해당 항목을 추가 측정한다.

첫 예비 단계(복원·1봇 호환·원시 계측)는 30~60분 이상이 필요할 수 있고 도구 문제는 별도다. A~C만 4개 정원에서 약124분의 예열·측정이며, 접속·복원·재기동·추가 시험·반복을 합치면 반나절 이상으로 잡는다. 실패한 상위 단계는 중단하므로 일정을 여러 점검 창으로 나눌 수 있다.

**실행 순서:** 격리 복원·원본 경로 대조 → 1봇 호환성 → 계측 신뢰성 → 0명 기준선 → 5명부터 상승 → 경계 재시험·지속 부하 → 운영 복구 확인 → 정원 결정. 기본 A~C 결과 이후에 경계 반복과 지속 부하를 진행하며, 결과 확인 전 운영 정원을 올리지 않는다.
